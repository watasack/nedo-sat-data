## 4. 踏んではいけない罠

### レビューの回し方

- **事業性・審査員のレビューは提出物本文を書き換える。事務局レビューと同時に回さないこと**（同じファイルを触って衝突する）。
- **他セッションが並行しているときは、レビューを回す前に必ずブランチを同期すること。** 2026年8月9日、事務局レビューのマージと6分違いで審査員レビューを走らせ、**古い版の提出物を採点させた**（結果的に9件とも現行版で成立したが、再検証の手間が発生した）。

### 数値の扱い

- **手で数えない。** 3本のスクリプトで実測する:
  - `python3 ../count_chars.py 12_提出版_様式4.md` — 設問別の本文字数
  - `python3 simulate_landing.py` — 質問4が(B)のときの着地。**手順の正本はこのスクリプトの `OPS`**。12の一覧と食い違ったらスクリプトが正しい
  - `python3 count_fig_chars.py` — 図の中に載る文字数（質問4が(C)のとき要る）
- **12で数値を持つのは「見出しの字数注記」と「回答別の着地」節の2箇所だけ**である。他の場所に数値を書くと、本文を直すたびに陳腐化する（テーマ1で4回再発した）。
- **推測値を書かない。** 特に金額。取れていないものは「未取得」と書く。

### 提出物の中身

- **本文に足すなら同じ設問から抜く。** 5設問とも493〜500字で空きが無い。
- **図の中にファイル名や他図への参照を書かない**（テーマ1で混入させて作り直した）。
- **図を直したら `count_fig_chars.py` を回して着地節の4値を更新する。**
- 「世界初」は使わない。**「先行がある」は減点事由ではない**（様式4の④の審査項目が括弧書きで「既存システムの機能性向上・組み合わせも含む」と明記している）。問うべきは「先行に対して粒度・頻度・コスト・意思決定への接続のどこで優位か、1行で言えるか」。

### 技術

- **workflow_dispatch API はこの環境では403。** Actions は `trigger-*` ブランチへの push で起動する。
- **GitHubは1ファイル100MB超でブランチ全体を弾く**（pre-receive hook）。取得スクリプトには必ずサイズ上限を入れる（`fetch_bid_refs.py` に40MB上限の実装がある）。
- **PoCの教訓**: Landsat 8/9 単独では、画素単位の雲マスクをかけると観測ギャップの中央値が40〜48日になり、③の「±10日」を支えられない。**Sentinel-2を足して共通グリッド（UTM 30m）へ再投影して初めて20日になる。** `fetch_snowmap_poc.py` 参照。
- numpy 2.x: `np.trapz` は廃止、`np.trapezoid`。
- PDFのテキスト化は `pdftotext -layout`（`pypdf`/`pdfminer.six` はこの環境では壊れている）。
- 事務条項の判断は必ず `../koubo/` の原文に当たる。

## 5. やらないこと

- **提出物本文の大幅な書き直し。** 3観点のレビューを通っている。触るなら必ずレビューを回し直すこと。
- **案そのものの再検討。** 5ラウンド・15案を潰して残った1案である（`01_検討経緯.md`）。新しい案を出す場合は7.1節＋8.2節の敗因の型7つを最初に当てること。
- **金額の推測値を書くこと。** 未解決B（契約金額）が閉じるまで「年商◯円」は書かない。
- **海外展開の深掘り。** 1〜2行に留める方針が8.7節で決まっている。
