# NEDO 応募書類のレビューサイクルを1周回す

`.claude/agents/nedo-secretariat-reviewer.md` を呼んで指摘を受け、対応し、記録し、コミットするまでが1周。
**このスキルの主目的は、同じ型の指摘が何度も出るのを止めることである。**

テーマ2で9サイクル・53件を要したが、**うち9件は同じ型の反復**だった。
毎サイクルの「学び」を記録に書いてはいたが、書いただけで既存箇所を横断点検しなかったため再発した。
手順3がその再発を止めるためにある。**飛ばさないこと。**

## 対象テーマの解決

| テーマ | 提出実体 | レビュー記録 | 指摘番号 |
|---|---|---|---|
| テーマ1（保温システム劣化監視） | `12_提出版_様式4.md` | `review_v4_様式適合.md` / `review_v3_事務局視点.md` 文末 | N-n |
| テーマ2（融雪型火山泥流の積雪水量） | `theme2_ライフライン復旧/12_提出版_様式4.md` | `theme2_ライフライン復旧/review_t2_様式適合.md` | T-n |

引数でテーマが指定されなければ、直近に変更された方を対象にしてよいか一言で確認する。

## 手順

### 1. 前提を集める

- レビュー記録を読み、**最後のサイクル番号と最後の指摘番号**を得る（次はその続き）
- `git log --oneline -5` で**直前のサイクル以降に何を変えたか**を把握する
- 提出実体の現在の字数を測る: `python3 count_chars.py <提出実体>`

### 2. サブエージェントを呼ぶ

`nedo-secretariat-reviewer` を `Agent` ツールで呼ぶ。**このサブエージェントの定義はテーマ1向けに書かれている**ので、テーマ2をレビューさせるときは冒頭で対象と物差しを明示的に上書きすること。プロンプトには必ず以下を入れる。

1. **対象ファイルの絶対的な指定**と、提案の中身の1段落要約
2. テーマ2なら「**懸賞金・審査項目・テーマ記述はテーマ2の行を読むこと**」（システムプロンプトのテーマ1固定の記述を無効化する）
3. **レビュー記録のパスと「T-1〜T-nnは対応済み。再指摘しないこと。ただし対応済みの根拠は現物であり記録の記述ではない」**
4. **今回のサイクル番号と、振るべき指摘番号の開始値**
5. **直前のサイクルで何を変えたか**の箇条書き（これを書かないと古い前提でレビューされる）
6. 本文への指摘が続けて0件なら「**無理に指摘を作らないこと。0件と言い切ることはこの工程の正常な終点である**」

参考の雛形は `reference/prompt-template.md` にある。

### 3. 指摘に対応する（横断点検を含む）

**指摘をそのまま実装しないこと。** 順に:

1. **指摘の当否を現物と原典で確かめる。** レビューアは `koubo/` は読むが、提案の根拠資料（`01_検討経緯.md` の原典整理）までは精査しない。
   テーマ2のT-27は、指摘（本文と図で量が違う）を追った結果**その下に別の問題（図の実測点が原典に無い派生値だった）**が埋まっていた。
2. **修正する。**
3. **横断点検する。** ここが再発を止める要。下の「同型再発の一覧」を毎回通す。

#### 同型再発の一覧（毎サイクル、対応後に必ず通す）

| 型 | 点検すること |
|---|---|
| **共通文書の追随漏れ**（5回出た） | テーマ側で**分岐・期限・数値・質問構成**を変えたら、`04_事務局照会文案.md`・`10_提出様式メモ.md`・**もう一方のテーマの `12_提出版_様式4.md`** の3つを必ず開いて突き合わせる |
| **必ず不合格になるチェック**（4回出た） | チェック項目を**1つ足したら**、既存の全分岐の下でそれが実行可能かを確かめる。分岐は少なくとも3系統ある——**応募者区分**（法人／個人／グループ。個人用は様式番号も欄も違う）、**質問4の回答**(A)(B)(C)、**図表の有無** |
| **数値の数え方が同じ場所にない**（3回出た） | 数値を書いたら、**何を数えて何を数えなかったか**を同じ文に書く。「実測」と称した値は必ず再現できること |
| **図を直したときの波及**（8回出た） | 図に触れたら **本文・軸ラベル・凡例・図の見出し・キャプション** の5箇所を突き合わせる。図の中にファイル名や他図への参照が無いことも目視 |
| **もう一方のテーマからの移し忘れ** | チェックリストを触ったら、もう一方のテーマの同種リストと項目単位で突き合わせる（第9サイクル後の自主点検で3件出た） |

#### 字数を動かしたときの必須作業

本文を1字でも変えたら:

1. `python3 count_chars.py <提出実体>` で測る
2. **見出しの字数注記**を直す
3. **「回答別の着地」節の表と着地値**を直す。着地値は**手順を実際に適用して測り直す**（見込み値を書かない）
4. この2箇所以外に字数値を書かない（テーマ1で散らばって4回再発した）

### 4. 記録する

レビュー記録に追記する。書式は既存の節に合わせる。**必ず入れるもの**:

- サイクルの推移表に1行（件数・致命的・重大・到達点）
- 指摘ごとに「何が問題で、何を根拠に、どう直したか」
- **このサイクルの学び**（同型再発の一覧に足すべき型が見つかったら、上の表にも追記する）
- 字数が動いたなら新しい実測値

### 5. コミットする

- ブランチは作業中のもの（テーマ2なら `claude/theme-2-review-sxjn9w`）
- コミットメッセージは**指摘番号・何が問題だったか・どう直したか**を重大度ごとに。字数が動いたら新旧を書く
- `git push -u origin <branch>`

### 6. 続けるか打ち切るかを決める

**打ち切ってよい条件**（テーマ1のように0件到達まで回す必要はない）:

- 提出物**本文**への指摘が数サイクル連続で0件
- 残る指摘が軽微のみで、内容が転記されない `>` 注記や【提出時に削除】節の内部
- 投じる労力に対する戻りが落ちている

打ち切るときは**記録にそう書く**（「0件に到達した」と「ここで打ち切った」は別物である）。

## やってはいけないこと

- **指摘を鵜呑みにして実装する。** 当否を現物と原典で確かめる。レビューアの数値が間違っていたことがある（テーマ2 T-42 の逆で、こちらの集計漏れだったこともある）
- **横断点検（手順3-3）を飛ばす。** これを飛ばすとサイクル数が倍になる
- **提出物本文に字数値を散らす。** 見出し注記と着地節の2箇所だけ
- **図の中にファイル名・他図への参照を焼き込む。** 両テーマで実際に混入して作り直した
- **「実測」と書いた数値を再現せずに残す**
