# 説明資料をレビュー1〜2回で仕上げる

**このスキルの目的は「良い資料を作ること」ではなく「ユーザーのレビュー回数を減らすこと」である。**
資料の見栄えを上げても、レビューが5回走れば失敗である。

## レビューが増える3つの原因と、それぞれの対策

| 原因 | 何が起きるか | 対策 |
|---|---|---|
| **1. 知り得ない事実を推測で埋める** | 社名・体制・予算・公開可否を勝手に書き、指摘されて直す。1件ごとに1往復 | **T番号の未確認箇所**（下記）。推測しない。埋めずに番号を振る |
| **2. 読み手と依頼が未確定** | 構成ごと作り直しになる。**最も高い**（1回で資料1本分） | **着手前に3問だけ聞く**（下記）。ここだけは質問してよい |
| **3. 数字の根拠を聞かれる** | 「その数字の出所は」で往復。社内で他人からも聞かれる | **確度ラベル**（確定／仮定／未取得）を全部の数字に付ける |
| **4. 文章と表で説明してしまう** | 「分かりにくい。ポンチ絵を増やして」で**資料を作り直す**。原因2に次いで高い | **節ごとに図を1枚割り当てる**（下記・手順1.5）。文章は図の脚注にする |

原因3は資料が社内で回ったときにも効く。ラベルが付いていれば、読み手は仮定を仮定として受け取る。

**原因4はこのプロジェクトで2回起きている**（`60_shiryo/社内説明_NEDO応募.html` 第1版、`60_shiryo/日本気象協会_ご説明.html` 第1版）。
2回とも指摘の言葉は同じ——「もっとポンチ絵やイメージ図を多用して視覚的・直感的に」。
**書き手は正確さで満足し、読み手は理解しやすさを求める。** 表と確度ラベルは正確さの道具であって、
理解しやすさの道具ではない。両方要る。

## 手順

### 1. 着手前に3問だけ聞く（`AskUserQuestion` を使う）

**この3つは資料の構成そのものを変えるので、推測してはいけない。** 逆にこれ以外は聞かない。

1. **読み手と目的** — 1対1の相談／会議での正式な承認／部署・全社への周知。
   選択肢には**その構成の実物の断片を `preview` で見せる**（言葉で説明すると選べない）
2. **依頼（この資料で何を通したいか）** — `multiSelect: true`。依頼が無い説明資料は失敗する
3. **弱い部分をどこまで載せるか** — 本文に正直に／別セクションに集約／載せない。
   **既定は「本文に正直に」を推奨に置く**（社内資料は後で齟齬が出るコストのほうが高い）

読み手が決まったら分量を決める。**1対1の相談＝A4数枚相当・結論と依頼を先頭・根拠は `<details>`。
会議での承認＝決議事項を箇条書きで先頭・投資額とリスクと撤退条件を明示。
周知＝図と流れ中心・依頼は1つだけ。**

### 1.5. 書く前に、節ごとの図を決める（**省略しない**）

**節の一覧を作ったら、次にやるのは文章ではなく図の割り当てである。**
「この節は図1（○○を描く）」と全節に書き出し、**図が付かない節については、なぜ文章だけで足りるのかを言えること**。
言えないなら、それはまだ自分が機構を理解していない節である（文章は曖昧なまま成立するが、図は1本に決まる）。

目安: **本文3〜4段落につき図1枚。A4数枚相当の資料で図4〜7枚。** 表しかない節は失敗である。

このプロジェクトで実際に効いた図の型（`20_theme1_保温劣化監視/poc/out/fig/README.md` の9枚と、
`60_shiryo/` の資料が到達した形）:

| 型 | 何を描くか | どの説明に使うか |
|---|---|---|
| **ポンチ絵（機構図）** | 対象そのものを絵で描き、**不確定項の番号を絵の中の位置に置く** | 「何を見ているのか」。文章で3段落かかる説明が1枚で終わる |
| **断面図・縦軸のある絵** | 標高・深さ・階層など、実際に縦方向を持つ対象 | 「なぜ現状の手段が届かないか」（届いていない矢印を描く） |
| **比較バー（対数軸可）** | 信号と雑音、現状と提案、規模の比較 | 「大きいのか小さいのか」。**必ず判定線（破線）を1本入れる** |
| **タイムライン・時系列** | 観測日の飛び／工程／期限 | 「間に合うのか」「どれくらい粗いのか」 |
| **位置づけ図（2×2・並置）** | 自案と他案、2テーマの関係 | 「どこが違うのか」 |

**図の作法**（`artifact-design` の上に足す、この用途固有のもの）:

- **インラインSVGで書く**（外部画像はCSPで読めない）。色は必ずトークン経由（`var(--ink)` 等）で、
  明暗の両方で成立させる。`fill="#333"` のような直値は暗色テーマで消える
- **1枚に1つの主張。** 図の見出しは主張そのものを書く（「図3 誤差の内訳」ではなく
  「図3 何を引くと雑音がどこまで落ちるか」）
- **判定線を入れる。** 読み手が「で、これは良いの悪いの」で止まらないようにする
- **キャプションで結論を言い切る。** 図を見て分からなくても、キャプションだけで意味が通ること
- **図の中にファイル名・他図への参照を書かない**（提出物で実際に混入させて作り直した）
- 数値は必ず図の中にも書く（軸を目で読ませない）

#### 図のクオリティ ── 「チープ」と言われないために

**原因4を直して図を入れても、その図が記号の羅列だと「チープで実態がイメージできない」と再度差し戻される**
（2026年8月12日、日本気象協会向け資料の第2版で実際に起きた）。
**箱と丸で対象を代用しないこと。** 具体的には:

- **対象そのもののシルエットを描く。** プラントなら蒸留塔（胴＋段のリング＋頂部の鏡板）・球形タンク（脚つき）・
  浮屋根タンク・パイプラック・フレアスタック（炎とグロー）・煙突（識別帯）。山なら稜線・谷筋・雪線・噴気。
  **10〜20個の部品を置くだけで「その業界の絵」になる。** 四角と丸を4つ並べた図は記号であって絵ではない
- **計器の出力に見せる。** 熱赤外の話なら**熱赤外のパレット（暗紫→赤紫→橙→白）とカラーバー**で描く。
  可視と計測を**並置**すると「何が見えるようになるのか」が1枚で伝わる（この資料の図2がその形）。
  ただし**模式であることを図の中に明記する**（実画像だと誤解されると後で高くつく）
- **面（グラデーション）・奥行き（遠景を薄く）・光源（フレアや太陽のグロー）・素材（金属・雪の粒状）** を入れる。
  `<defs>` にグラデーションとフィルタ（`feGaussianBlur`／`feDropShadow`）をまとめ、全図から `url(#…)` で参照する
- **注記は面の外に出す。** 暗い絵の上に本文色の文字を置くと消える。**面の中に置くのは番号バッジと短い一言だけ**にし、
  番号の意味は面の外の凡例で説明する（この2つを混ぜて実際に文字が消えた）
- **背景と対象の明度差を先に決める。** 夜景・暗い面の上に対象を置くと、雰囲気を出そうとして両方が暗くなり
  「背景と対象の色が近くて見えない」になる（実際に指摘された）。**背景は思っているより暗く、対象は思っているより明るく**置く。
  目安として、シルエットの本体は背景の最も明るいところより**さらに2〜3段明るい**値にする
  （このプロジェクトでは夜空 `#0B131C` に対し鋼材 `#7A93A6`）。雰囲気は光源（フレア・灯り）で作れば足りる
- **暗い面・明るい面の中の文字色は固定値で持つ。** 面の背景がテーマで反転しない絵（夜景・熱赤外像・雪）は、
  背景も文字色も固定値にする。トークンで塗ると片方のテーマで読めなくなる
- **「同じものを別の見方で」は、図形を1つだけ書いて2回置く。** `<defs>` に `<g id="scene">` を1つ定義し、
  部品の色を `fill="var(--c-steel,#…)"` のように**CSS変数＋既定値**で書いておく。
  `<use href="#scene" style="--c-steel:…; --o-hot:0">` を2つ置けば、**幾何は完全に同一で配色だけ違う**2枚になる
  （「左右は同じ設備です」という主張が、図の作り方そのもので保証される。コピペで2回描くと必ずずれる）。
  `--o-…` を0/1で切り替えれば、片方だけに要素（保安灯・劣化部）を出せる
- **計測画像には計測画像の手掛かりを入れる。** 走査線パターン（`opacity` .1〜.2）、
  **画素グリッド**（分解能に対応する間隔＋「1画素 3.5 m」の注記）、
  **注目部の拡大インセット**（10〜40個の矩形を手で並べて画素として見せる）、カラーバー。
  この3つが入ると、線画が「センサの出力」に見える
- **図の品質は「一番良い図」ではなく「一番低い図」で判断される。** 1枚に力を入れると、
  その1枚が基準になって他が全部チープに見える（実際に「図2だけクオリティが高く他が追随できていない」と指摘された）。
  **揃える手段は2つで、どちらも `<defs>` に資産を置くこと**:
  1. **場面（絵）は1つ作って使い回す。** 主役の絵を `<g id="scene">` に置き、全体像の図では
     `transform="translate(…) scale(0.8)"` で縮小して同じものを出す。**絵が一致していること自体が
     「同じ対象の話をしている」という情報になる**（別々に描くと、読み手は別物だと受け取る）
  2. **記号の語彙を1組だけ作る。** 24×24の記号（雲・外装板・画素・センサ・熱源・塔1本・塔2本・衛星・
     観測所・書類・歯車…）を `<defs>` に定義し、**棒グラフの軸ラベルの横や凡例にも同じ記号を置く**。
     グラフと絵が同じ記号でつながると、図の一式が1つの体系に見える。
     線は `stroke="currentColor"` にして、置く側で `color="var(--…)"` を指定する
  - **注意**: `<use>` が `<g>` を参照するとき **`width`/`height` は効かない**（`x`/`y` の平行移動だけ）。
    大きさを変えるなら `<g transform="translate(…) scale(…)"><use …/></g>` で包む
- **描いたら必ず自分の目で見る。** ブラウザで開いてスクリーンショットを撮り、
  **文字の重なり・面外へのはみ出し・暗背景に暗文字**の3つを潰してから公開する。
  座標を計算しただけで公開すると必ずどれかが起きている

### 2. T番号の未確認箇所を置く

**自分が知り得ない事実は、埋めずに番号を振る。**

- 本文では `<span class="tbd">T3: 開発期間に当てられる人数</span>` の形で置く
- **資料の冒頭に「この資料を人に見せる前に埋める箇所 — N件」の枠**を作り、T1から順に
  「何が必要か」と「なぜ必要か」を1行ずつ並べる
- **返信の書式を枠の中に明示する**: `T1=株式会社◯◯ / T3=2名（うち専任1）`。
  これでレビューが「どこが違うか探す作業」から「番号に値を入れる作業」に変わる
- 枠には**「埋め終わったらこの枠ごと削除します」**と書く（`@media print` でも隠す）

T番号にするものの典型: 正式名称・組織の区分・体制と人数・単価や予算・対外的な名義・
どこまで書いてよいか（守秘や情報公開の制約）。

**6件を超えたら設計を疑う。** 多すぎるのは、そもそも聞くべきことを質問1回にまとめられていない兆候である。

### 3. 数字に確度ラベルを付ける

3段だけ。増やさない。

| ラベル | 意味 |
|---|---|
| `確定` | 一次資料の原文、または再現できる自前計算で確認済み |
| `仮定` | 幅で置いている。1点に決め打ちしていない |
| `未取得` | まだ根拠がない。**埋めていないことを明示する** |

**`未取得` のものを断定して書かない。** 資料の中に「数字の読み方」節を置き、3段の意味を1行ずつ説明する。
このプロジェクトの規約（`CLAUDE.md`「書き方の約束」）と同じ規律を、社内資料にも持ち込むということである。

### 4. 書く

- **出力先は `60_shiryo/<用途>.html`**（リポジトリのルートを番号で汚さない）
- `Artifact` ツールで公開する。**その前に `artifact-design` スキルを読む**（ページ設計の較正）
- **`<!doctype>` `<html>` `<head>` `<body>` は書かない**（公開時に包まれる）。`<title>` は書く
- テンプレートと実例は **`60_shiryo/社内説明_NEDO応募.html`** を読むこと。
  トークン定義・明暗3状態・確度ラベル・T番号の枠・印刷用CSSがそろっている。**流用してよい**
- 日本語のWebフォントはデータURIに埋めると数MBになるので**埋めない**。
  見出しに明朝、本文にゴシックのシステムフォントスタックを当てる（社内文書の格が出る）

### 5. 渡すときに、レビューの入口を1つに絞る

報告の文面で**「見ていただきたいのはT1〜Tnの値だけです」と明示する**。
これを書かないと、読み手は資料全体を校閲しようとして往復が増える。

構成そのものへの意見が出た場合は、**手順1の3問のどれを外したかを特定してから直す**
（表現の問題として直すと同じ齟齬が再発する）。

## やらないこと

- **推測で事実を埋める。** T番号にする。1件の推測が1往復を生む
- **読み手を確認せずに書き始める。** 構成の作り直しが最も高い
- **文章と表だけで説明する。** 表は正確さの道具であって理解の道具ではない。**節ごとに図を割り当ててから書く**
- **図を「補足」として最後に足す。** 足した図は本文の言い換えにしかならない。図を先に決め、文章をその脚注にする
- **確度ラベルなしで数字を書く。** 社内で必ず出所を聞かれる
- **T番号の枠を作らずに未確認箇所を散らす。** 探す作業をユーザーに渡すことになる
- **絵文字を節の見出しに使う／全部を中央寄せにする／角丸を全要素に付ける。**
  `artifact-design` が挙げている「AIが作った資料」の見え方に寄る
- **`60_shiryo/` の外に出力する**（次に探せなくなる）

## 版を重ねるとき

T番号の値が返ってきたら、**差し替えたうえで冒頭の枠を削除し、末尾の版表記を更新する**。

**再公開するときは `Artifact` に `url` を渡すこと。** 同じファイルパスで呼び直して同じURLになるのは
**その資料を公開したのと同じ会話の中だけ**である。**別のセッションから `url` なしで呼ぶと新しいURLが
発行され、ユーザーが既に社内へ共有したリンクは古い版のまま取り残される**（本人は更新したつもりでいる）。
既存の資料のURLは `CLAUDE.md` のファイル一覧に記録してある。分からなければ `action: "list"` で探す。

**T番号は版をまたいで再利用しない。** 新しい未確認箇所が出たら次の番号を振る
（同じ番号が別のものを指すと、過去のやりとりが読めなくなる）。
