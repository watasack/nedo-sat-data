# 共通スクリプト

両テーマで使うスクリプト。リポジトリルートから実行する。

| スクリプト | 用途 |
|---|---|
| `count_chars.py` | 提出実体の本文字数を測る。`python3 40_scripts/count_chars.py 20_theme1_保温劣化監視/12_提出版_様式4.md` |
| `audit_poc_numbers.py` | 文書が引用するPoCの数値が `poc/out/*.json` のどのキーに戻れるかを追跡する。引数なしでPoC結果を引用する文書を一括検査 |
| `download_poc_data.py` | PoC用の衛星データ・気象データを取得する |
| `fetch_*.py` | 提案の根拠となる一次資料（官公庁PDF・統計・過去回受賞情報等）を取得する |

## 参考資料の取得は、ローカルで直接実行してよい

```bash
python3 40_scripts/fetch_b2.py
```

**GitHub Actions を経由する必要はない。**

### なぜこの注意書きがあるか

当初の作業環境（クラウドサンドボックス）は、mlit.go.jp / env.go.jp / gsi.go.jp / meti.go.jp /
e-Gov 等への egress が 403 で遮断されていた。そのため次の三重の迂回を取っていた。

1. ネットワーク制限のない Actions ランナーで取得する
2. `workflow_dispatch` API も 403 だったため、`trigger-fetch-*` ブランチへの push で起動する
3. 取得結果を専用ブランチ（`b2refs`、`market-refs` 等）へ force-push し、
   手元からは `git show origin/<branch>:<path>` で読む

この方式は取得系統ごとにワークフローとブランチを1組ずつ増やすため、**ワークフロー49本・
ブランチ130本**に膨れ、リポジトリの履歴は 2.6GB、clone に30分以上かかる状態になった。
本線（HEAD）から到達できるオブジェクトは1,266個・約20MBに過ぎず、**残りはすべて
サイドブランチ上の収集データ**である。

2026-08-11 に、ローカル環境（Claude Code）から対象ホストすべてへ到達できることを確認した。

| ホスト | 結果 |
|---|---|
| www.mlit.go.jp / www.env.go.jp / www.gsi.go.jp / cir.nii.ac.jp | HTTP 200 |
| elaws.e-gov.go.jp | HTTP 301（正常なリダイレクト） |
| www.meti.go.jp | 素の UA では 403、スクリプトが使う通常の UA では 200 |

実証として `fetch_plateau_refs.py` をローカルで実行し、**22/22 取得成功**（mlit の PDF、
PRTIMES、東京都都市整備局の PDF を含む）を確認している。

### したがって

- 新規の取得は**ローカルで直接実行する**。ブランチを増やさない。
- 既存の `origin/*-refs` 等のブランチにある取得済み資料は、引き続き
  `git show origin/<branch>:<path>` で参照できる（文書からの引用が残っているため削除していない）。
- Actions 経由が要るのは、ローカルの回線から届かないホストがある場合等に限られる。

### 未整理の課題

- `.github/workflows/` の `fetch-*.yml` 49本は、上記の迂回のために作られた一回限りの
  ワークフローであり、現在は不要。1本の汎用ワークフロー（スクリプトパスを入力に取る
  `workflow_dispatch`）へ集約するか、削除してよい。
- 収集データを載せた130本のブランチは、履歴 2.6GB の原因である。文書からの引用を
  一次資料ごと本線へ取り込むか、参照が切れてよいものを整理すれば大幅に軽くできる。
  **引用が残っているため、確認せずに削除しないこと。**
